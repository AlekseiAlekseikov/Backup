найдены только исполнением сгенерированного скрипта в настоящем `sh` (`Iter50Stand.kt`).

| # | дефект (что было) | следствие на устройстве | исправление |
|---|---|---|---|

## 3. §5.1 — TTL: argv и политика

| # | дефект | следствие | исправление |
|---|---|---|---|
| 1 | `iptables -D POSTROUTING $spec` внутри цикла с `IFS=<newline>` | `-o wlan0 -j VAPP_TTL` уходило **одним** argv → реальный iptables отвергает вызов → своё правило остаётся, OFF заявляет FAILED | `split_spec` (whitelist символов, без `eval`) + `del_jump` (разбор внутри `set -- $spec`) |
| 2 | пустой `rc` в `need_rb` трактовался как «rc≠0» | ложный `TTL_ROLLBACK` в журнале при штатной остановке | `rc_a/rc_j/rc_a6/rc_j6=skip` при `TTL_STOP=1`, rollback только при `TTL_STOP=0` |
| 3 | `OWN_LEFT_STOP` проверялся **после** `SCOPED_OK` | при неснятом своём правиле печатался «успех» (`SCOPED_OK`), т.к. в таблице стояло корректное правило от прошлого раза | `OWN_LEFT_STOP` раньше всех «успешных» вердиктов; `TtlVerify` маппит его в `FAILED` с причиной «своё правило снять не удалось…» |
| 4 | `${NOT_OWNED// /}` (bashism) | на `#!/bin/sh` = dash это `Bad substitution` → скрипт **обрывался посередине** (найдено только исполнением, rc=2) | POSIX-проверка `[ -n "$NOT_OWNED" ]` |

Политика подтверждена сценариями `Iter50TtlArgvTest` (8 тестов, все на исполнении):

* ON → OFF: `TTL_DEL family=v4 spec="-o wlan0 -j VAPP_TTL" rc=0`, `TTL_OFF result=OK`, таблица пуста,
  в журнале argv видно `<-D> <POSTROUTING> <-o> <wlan0> <-j> <VAPP_TTL>` (раздельные argv);
* повторный ON: ровно одно правило и один переход (без дублей);
* чужое (`-o wlan0 -j TTL --ttl-set 64`, отдельная цепочка `XOTHER`) переживает ON+OFF байт-в-байт;
* **отказ `-D`** ⇒ `TTL_TRY action=stop reason=v4_own_not_removed`, ни одного `-A`/`-N` после отказа,
  `VERDICT=OWN_LEFT_STOP`, разбор для UI = `FAILED`;
* отказ чтения (`-S` падает) ⇒ `READ_V4=failed`, `result=UNKNOWN` (не «правил нет»);
* `-g` не считается нашим переходом; переход с кавычками/match не удаляется, цепочка сохраняется.

## 4. §6.1/§6.3 — «сохранено» и положение тумблера

### 4.1. Ложное подтверждение записи

Было: `stores` считал успешные `commit()`, а `confirmed` строился **только по readback**. Так как
`SharedPreferences.Editor.commit()` может вернуть `false` уже после изменения in-memory состояния,
возможна была ситуация `confirmed=true, stores=0`.

Стало (`Prefs2.copiesOf/CopyFact/putBooleanCore/removeCore/putStringCore/putBoolAndBumpCore`):

* копия = `Copy(name, prefs)`, недоступная копия — `prefs == null` (**не** «пустые настройки»);
* **`confirmed` = `committed && revOk && valueOk` в ОДНОЙ И ТОЙ ЖЕ копии**; `stores` — число
  реальных `commit()`, `readback` — число копий, где значение просто прочиталось;
* `stores=0 && readback>0` печатается как `reason=commit_false_readback_only:N`, а не как успех;
* `removeEx` подтверждается только отсутствием ключа **вместе** с tombstone в записавшейся копии;
* транзакция intent+generation подтверждается только если **обе** части верны в одной копии,
  иначе `gen=-1` (фиктивное поколение не выдаётся);
* `nextGen`: переполнение/неизвестное предыдущее значение не превращается в отрицательное;
* `dps` с фоллбэком на CPS заменён на `dpsOrNull`: одна физическая копия больше не считается
  двумя `stores` (в direct boot теперь честное `partial`).

Тесты (`Iter50Prefs2Test`, 13 шт.) исполняют **настоящий** код `Prefs2` на поддельных
`SharedPreferences` с моделью «commit=false, но память изменена», отказом/исключением в одной
копии, частичным применением транзакции, равными ревизиями с разными значениями и недоступной
второй копией.

### 4.2. §6.3 — положение тумблера при `unknown`

## 6. §7 — JIT: что я сделал и чего сознательно НЕ сделал

**Честно: опасная цепочка JIT в этой итерации не изменялась.** Причина — не «не успел», а мандат
§7.3/§0: нельзя выдавать недоказанную безопасность за безопасность, а на руках нет ни ГУ, ни
транспорта, на котором можно проверить отмену или гарантированное отсутствие позднего выполнения
`ctl.restart zygote`.

Что **фактически** есть в коде (проверено чтением, `JitNetCore.kt`):

* состояние операции существует и пишется в хранилища: `OpMark(op, ts, want, state)`,
  состояния `sending → replied | undefined`; `assessStored()` даёт `NONE | UNREADABLE | AMBIGUOUS |
  BROKEN_SNAPSHOT | UNDEFINED | PENDING` (проверяется `JitIter*Test`);
* новый клик при `undefined` **блокируется** (`chain_undefined`), выход — только по проверяемому
  признаку (старт zygote после отметки) или по истечении окна, и он **назван выходом, а не
  доказательством** (`JIT_OP_ABANDONED … late_answer_possible=1 snapshot_reused=no`);
* поздний ответ не может быть приписан новой операции (сверка `op` id в `onLateOutcome`);
* старый снимок Wi-Fi не применяется автоматически на независимом старте.

Чего **не доказано** и что нельзя утверждать после этой итерации:

| вопрос §7.2 | статус |
|---|---|
| доставка/начало/завершение/отмена конкретной команды | ⛔ не доказуемо доступными средствами; `getprop`, новый PID, boot id, IP/Wi-Fi, timestamp zygote — **не** доказательства |
| «позднее выполнение уже случилось» | ⛔ не наблюдалось и не проверялось (нет ГУ) |
| фактическая JIT-компиляция | ⛔ способа проверки на целевой прошивке нет; `dex` в maps / работающий Wi-Fi — не доказательство |
| восстановление исходного Wi-Fi | 🟡 механизм есть (снимок + продолжение по клику), на устройстве не проверялся |
| `umount -l` и namespaces JIT-хранилищ | 🟡 реализовано, обратимость на прошивке не доказана |
| два zygote/PID reuse/смена часов | 🟡 `ZygoteStart` — только диагностический сигнал (uptime + starttime), причинность не приписывается |

Что нужно от владельца, чтобы этот пункт закрыть (без новых кнопок, только существующий JIT-тумблер):
1) один клик JIT на 1.0.63 с последующей выгрузкой журнала (`JIT_CLICK`, `JIT_OP_ABANDONED`,
   `JIT_*` строки) — это даст факт «как ведёт себя цепочка на этой прошивке»;
2) отдельно — попытка проверки компиляции (`dumpsys package`/`cmd package compile`-подобные
   read-only средства) с фиксацией результата; если read-only проверки нет — так и записать.
