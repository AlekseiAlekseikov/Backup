## 2. §4.1 — снимок состояния тумблеров (причина найдена по коду + логу 1.0.61/62)

**Причина.** `tools.state` отправлялся только из обработчиков клика. При холодном открытии панели снимок не приходил вовсе, и UI подставлял `def` — 17 из 19 тумблеров выглядели «выключенными», хотя включённые были в настройках. Второй дефект: `seq` выдавался **после** формирования `tools.state()`, поэтому старый (медленный) снимок получал **больший** номер и перебивал новый.

**Исправление (по причине, не по раскраске):**
- `ui/UiBridge.kt:837,859,888,905` — номер берётся **в момент запроса**, доставка разрешена только через `markToolsStateDelivered(seq, reason)` (CAS); отказ пишется как `TOOLS_STATE_STALE seq=… delivered=…`, а не «тихо применяем».
- `tools/ToolsBackend.kt:150` — `revision()`/`writeRevision`: снимок идёт с ревизией; инкременты в `set(Toggle)`, `set(Choice)`, `setBrightness`, `setRest`, `setKeepAwake`.
- `tools/ToolsBackend.kt:233` — снимок сам сообщает состав (`$keys`) и ревизию (`$rev`): зашитая константа «19» расходилась с реальным `state()` и давала ложное «снимок неполный». `ui/ToolsPanel.kt:158–172` — `stateRenderedKeys`/`stateExpectedKeys` считаются **по ключам**; `unknownToggle = raw == null` — неизвестность показывается по каждому ключу отдельно, включая частичный/повреждённый снимок. Нейтральная строка вместо красного текста и без новых кнопок.
- Клик одного тумблера не переписывает другие: снимок обновляется целиком из ревизии, а не «по факту клика».

**Таблица тумблеров** — в Приложении A (все 19 ключей состояния панели «Инструменты»: источник, поведение после старт/update/sleep/boot, зависимость отображения).

**Тест:** `Toggles45UiTest` (7) + `Iter46Test.saveSnapshotKeepsPerKeyUnknown`-класса проверки (см. §11, пункт 1).

🟡 **Проверено:** JVM (порядок номеров, CAS, неизвестность по ключу). **Требует машины:** как реально выглядит панель при холодном открытии на 1.0.63.

## 3. §4.2 — CPS/DPS: последняя запись побеждает

**Причина.** `Prefs2.getBoolean` = `cps || dps`. Старое `true` в одной копии перебивало новый `OFF` в другой — прямо видно в логе: `master_remember_brightness=reg:true/dps:false`.

**Исправление.** `tools/Prefs2.kt:63,65,69` — ревизии `<key>#rev`; значение и ревизия пишутся **одной транзакцией**; чтение — `Toggles45.pickBoolean/pickString` (`tools/Toggles45.kt:40`): побеждает **большая ревизия**, при отсутствии ревизий (миграция с прежней версии) — прежняя семантика, чтобы сохранённые настройки не терялись. `diag()` (`Prefs2.kt:158`) печатает значение **вместе с ревизией** из обоих хранилищ.

**Границы честно:** атомарности между CPS и DPS нет (два независимых `commit()`), поэтому «сохранено» объявляется только после подтверждения чтением; «Процент заряда» → «Цифровая наружная» — это зависимость **отображения**, а не стирания настройки.

**Тесты:** `Iter46Test` — `newerOffWinsOverOlderTrue`, `legacyInstallKeepsOldSemantics`, `partialWriteOnOneCopyStillGivesLastIntent`, `equalRevisionsDoNotInventValue`, `stringsUseSameRule`. ✅

## 4. §5 — TTL: намерение владельца отдельно от факта

**Причина (лог 13.11):** клик терялся, если отказ (transport/root/сеть) случался **до** сохранения намерения; debounce и отказы «in-flight» отбрасывали последующие клики; факт `applied` из прошлого сеанса выдавался за текущий.

**Исправление:**
- `tools/TtlReconcile.kt:27,58,83,108,116,119` — политика «последнее намерение»: `onIntent` сохраняет намерение **всегда** (`MARKED_AND_RUNNING`, если применение идёт), `onRunFinished(success)` → добивание **последним** намерением, цепочка **≤ 3**, `onNetworkEvent()` → `networkDirty` (событие, пришедшее во время прогона, не теряется). Отмена **запущенного shell не заявляется**.
- `tools/NetworkTtl.kt` — намерение `ttl_65_ativo` + `applied=pending` пишется **первым**, до любых отказов; единый `applyForIntent(ctx, want, source)` (`:339`) для клика/добивания/сети; удалены debounce и отказы in-flight (осталась single-flight + цепочка); `finally` → `reconcile.onRunFinished(...)`; receiver → `reconcile.onNetworkEvent()`, при окне 30 с — **одноразовый** `networkRecheckOnce` (single-shot, не watchdog) → `reapplyForNetwork` (**не включает** при OFF).
- Факт: `ttl_65_applied` + `_pending_reason` + `_applied_at` + `_applied_boot` (`NetworkTtl.kt:60,97,114`). `PREF_TTL_65_APPLIED_BOOT` + `bootCount()`: при чужой/нечитаемой загрузке состояние = `pending`, ложного `applied` из прошлого сеанса нет. `bootRestore` ставит `pending` (`boot_unverified`) и `applied` только после фактического readback.
- Удаляются только свои scoped-правила (`oif wlan0`), Wi-Fi/CarPlay не выключаются, глобальных правил «на всякий случай» нет, диагностика сеть не меняет. **iptables ≠ TTL на проводе** — это прямо оговорено в отчёте и в логах.

**Тесты:** `Iter46Test` — `offDuringRunningOnIsNotLost`, `repeatedClicksApplyOnlyLastIntent`, `chainIsBounded`, `networkEventDuringRunIsNotLost`, `networkEventWhenIdleRunsImmediately`, `successfulApplySatisfiesIntent`, `appliedFactIsTiedToBootAndStaleAfterChange`. ✅
🟡 **Требует машины:** реальное снятие/возврат раздачи, смена сети, сон — на 1.0.63 не проверялось.

## 5. §6 — звук замка: временный отказ ≠ выключение намерения

**Причина (лог 13.11, `:5549`).** `bindDisabledUntilBoot` ставился без сброса, а `ERR_ROOT_CHANNEL_UNAVAILABLE` считался «детерминированным» — после одного отказа копирования (`copy failed rc=1 out=ERR_SCRIPT_UPLOAD_CLEA…`) звук не работал до ребута, хотя root позже был доступен.

**Исправление (`tools/LockSound.kt`):**
- `bindGen` (`:90,188,514`) — поколение растёт в `setEnabled`, `selectFileByName`, `onBootOrWatchdog`; задача старого поколения не монтирует и **не затирает** новый выбор (`LOCKSOUND_BIND_CANCELLED`).
- `recordBindFailure` (`:1010`) — **ограниченный идемпотентный** retry: один повтор с проверкой поколения и `isEnabled`, backoff `backoffMs` (`:1053`) = 5/10/20/40 с (≤ `MAX_BIND_RETRIES`), счётчик сбрасывается; «замок до boot» больше не ставится на временные отказы.
- `armRetryOnChannelReady` (`:1063`) — повтор, когда канал root реально вернулся (`AdbClient.onChannelReadyOnce`); `onConditionsRestored` (`:1083`) — при доказанном возврате условий. Шторма нет: один повтор на событие.
- `ERR_ROOT_CHANNEL_UNAVAILABLE` / `Permission denied` / `avc: denied` — **временные**, не «детерминированные».
- `applied` — только после readback; OFF → штатный звук, снимается **только своё**; `desired_off` пропускает bind.

**Тесты:** `Iter46Test.backoffIsBoundedAndGrows`, `offCancelsPendingWorkByGeneration`; плюс существующие тесты звука. ✅
🟡 **Требует машины:** слышимость в салоне, SELinux Enforcing, `update`/`sleep`/перезапуск. Про `uninstall` — честно: штатный звук возвращается, своих файлов после снятия приложения не остаётся, но проверить на ГУ я не могу. ⛔

## 6. §7 — JIT

Эта итерация добавляет к политике iter40–45 **одно** новое правило и ничего не «улучшает» без доказательств.

**Новое (§7.2):** `tools/JitNetCore.kt:1464` — `restoreMayEnableWifi(mark, now)`: **поздний независимый старт не включает Wi-Fi по сохранённому снимку**. Включать разрешено только продолжению конкретного клика (возраст отметки ≤ `WIFI_ENABLE_MAX_AGE_MS = 5 мин`). Отказ по причинам: `mark_absent`, `mark_ts_unreadable`, `clock_shift_back` (отметка «из будущего» — коррекция часов, не доказательство свежести), `late_start:<age>`. Вызов — в `runScheduledRestore` (`JitNetCore.kt:2191`): при отказе возврат идёт в режиме «не включать», `restoreWifi` (`:2317,2344`) не вызывает `setWifiEnabled(true)`, данные операции **не удаляются**, авто-повторов нет. Выключить Wi-Fi, включённый владельцем самим, мы тоже не будем.

**Политика завершения операции (без изменений с iter45, подтверждаю честно):**
- 15 минут (`STALE_MARK_MS`, `JitNetCore.kt:1436`) — **не доказательство завершения**, а граница разблокировки: дольше команда `setprop ctl.restart zygote` в очереди транспорта не живёт, и за это время владелец успевает сам изменить Wi-Fi. По истечении окна: `JIT_OP_EXPIRED … wifi_restore=none clicks=allowed` — старый снимок **не** применяется, авто-рестартов нет.
- Свидетельство завершения ровно одно — **ответ именно той команды** (поздний callback транспорта). Новый процесс, boot id, `getprop`, включённый Wi-Fi/IP, dex в `/proc/self/maps`, `SUCCESS` записи — не доказательства. Пока ответа нет — `chain_undefined`, новый клик блокируется, маркер **не стирается вслепую**.
- Вечной блокировки нет (`STALE_MARK_MS`), авто-рестартов и backfill после boot нет: после перезагрузки владелец включает тумблер сам.
- `ctl.restart zygote` — только внутри явного клика (в коде ровно одно место, тест `JitRefTest`).

**Что осталось 🟡:** гонки записи/откат CPS/DPS, «запись до проверки хранилищ», identity по hash объекта, перечитывание перед записью, чужие `pedido/auto` — в iter40–44 уже переписаны (`JitRef.commitConditional`, `assessStored`, `removeOwned`), но **новых правок в этой итерации я не делал** и заявлять их как проверенные на 1.0.63 не могу.
**Что осталось ⛔:** доказать факт JIT-компиляции нельзя ничем из доступного (нет `dex2oat`-подтверждения на ГУ); `umount`/namespace (§7.3) — данных нет, обратимость не заявляется, перезагрузка ГУ как лечение запрещена, повторный клик JIT — не средство восстановления Wi-Fi.

**Тесты:** `Iter46Test.lateStartNeverEnablesWifiFromSavedSnapshot` + весь набор `JitIter39/40/41/42/43/44`, `JitOrchestratorTest`, `JitPersistenceTest`, `JitRefTest`. ✅ (JVM)

## 7. §8 — журналы

### 7.1 `AppFileLogger` — ротация была **до** лока
**Причина.** `AppFileLogger.kt:117–132` (до правки) ротировал файл перед взятием лока, `catch (_: Throwable) {}` глотал отказ `delete`/`rename`/`sync`, `fsync` не вызывался. В ХВОСТЕ файла владельца 13.11 лежал блок `0x00` на 3296 байт ровно на границе смерти процесса (последняя строка `08:05:56.398`, следующий старт `08:06:17`). Первопричина **не доказана** (воспроизведения нет) — убраны оба правдоподобных механизма, повреждение детектируется.

**Исправление.** `tools/FileLogCore.kt` (новый) — запись как **одна** операция: JVM-очередь + межпроцессный лок на **отдельном стабильном файле** `<name>.lock` (ротация активного файла его не ломает) вокруг **выбора активного файла + ротации + записи + fsync**. Определённое поведение при недоступности лока: занят — **не пишем** (`process_lock_busy`, иначе появлялись «дыры» в общем offset), лок-файл создать нельзя — пишем, но с `unlocked:no_lock_file` в `reason`. `AppFileLogger.kt:121` — провал сообщается как `LOG_WRITE_FAILED` с причиной, `LOG_WRITE_UNLOCKED` — как предупреждение; **SUCCESS больше не подменяет провал**.
`AppFileLogger.kt:61` — **§8.2:** хвост проверяется на NUL **до** первой записи (`pre_init=true`); раньше init-строка писалась первой и могла замаскировать уже существующий нулевой хвост. NUL-блок не приписывается legacy-writer по имени — в коде и отчёте это сказано прямо.

### 7.2 `LogFiles`
`tools/LogFiles.kt:315` — `protectedSet`: активная часть защищена **всегда** (максимальный номер сегодняшней даты), даже если вызывающий не передал имя; раньше `activeName == null` означал «защиты нет». Жертвы по лимиту количества выбираются **после явной сортировки** «самые старые первыми» (раньше `drop()` применялся к списку «новые первыми»). Отказ `delete` **не** считается успехом — `LOG_PRUNE removed=FAILED … reason=…`. Отказ лока каталога публикуется как `LOGFILES_LOCK_UNAVAILABLE … action=write_under_jvm_lock_only`. Сохранены: fallback внешний→внутренний, новая часть до удаления старой, `.1000` как своя часть (`parseOwn`), полный диск (`space:*`), запись под локом.

**Тесты (§11, пункт 5):** `Iter46Test` — `appendsUnderLockAndReportsTruthfully`, `rotationKeepsPreviousPartWhenNewCannotBeCreated`, `rotationMovesWholeFileAndStartsNewOne`, `tailNulIsDetectedBeforeWriting`, `concurrentWritersDoNotInterleaveLines` (8 потоков × 60 строк, ни одна строка не потеряна/не склеена), `busyLockRefusesToWriteInsteadOfCorrupting`, `failedWriteIsReportedNotSilentlySwallowed`, `pruneDeletesOldestFirstAndSparesActivePart`, `thousandthPartIsStillOurOwnFile`. ✅
**Честность TTL-снимков** (начало/окончание, `pre_confirmed`/перекрытие/поздний/неизвестно, single-flight, trailing, один владелец диагностики) — в `NetworkTtl`/`TtlReconcile` (§4 этого отчёта), а не «дописана в лог». 🟡
**Сквозной тест `AppLog → файл` на Android** — недоступен в песочнице; `scripts/localjvm/check_applog.sh` проверяет только JVM-путь. ⛔

## 8. §9 — окна, AVAS, строка состояния, главный поток

- **`VENT_CLOSE_FAIL`** (`tools/WindowDoors.kt:537`) — переименовано в `VENT_CLOSE_UNCONFIRMED`: `getIntProperty` возвращает последнее известное значение VHAL, а применение команды приходит позже. Физический отказ **не утверждается** (`physical_failure=not_claimed`), опасных движений нет; добавлен **один** поздний readback через 1.5 с (не цикл), который только уточняет факт в журнале (`VENT_CLOSE_CONFIRMED_LATE` / `_STILL_UNCONFIRMED`).
- **AVAS** — отдельная **read-only** диагностика, в JIT не входит, mute не включается, `audioserver` и системные звуки не трогаются. Симптом 1.0.62 («вернулся, но в салоне не звучал») остаётся **объяснённым только как симптом AVAS**. ⛔ нужна машина.
- **Строка состояния** — по референсу: цифровой климат = уставка, `+12°` — заглушка, наружная = `AC_AMBIENT_TEMP` / `(raw−80)/2`, `ENV_OUTSIDE` как fallback (iter45, не менялось).
- **Главный поток:** `AdbClient.execute` с `main` на `SCREEN_ON`/`USER_PRESENT` устранён в iter45 — `VoiceAssistantService.kt:618` уводит работу в `BgWorker.post`, `onReceive` возвращается сразу. Проверено чтением кода и тестом `MainThreadTest`; на 1.0.63 на ГУ — не проверялось. 🟡

## 10. §7.3 `umount`/namespace — данных нет

`readlink /proc/<pid>/ns/mnt` и mountinfo до/после на ГУ **не снимались** (в этой сессии логов нет). Поэтому:
- обратимость `mount --bind` **не заявляется**; «пустой снимок в другом контексте» гарантией не считается;
- root не гарантирует namespace init;
- согласованное контролируемое испытание существующим тумблером **не проводилось**;
- повторный клик JIT — **не** средство восстановления Wi-Fi; перезагрузка ГУ как лечение **запрещена**.

⛔ Всё это — задача проверки владельцем (см. §12.5).
