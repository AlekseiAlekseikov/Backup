## 1. Что было сломано и что изменено (по причинам, с файлами)

### 1.1 §4 TTL: клик терялся навсегда — подтверждено кодом

**Причина (три отдельных дефекта, все видны на `66de8de`):**
1. `NetworkTtl.setTtl65Active` в `finally` вызывал `reconcile.onRunFinished(lastApplyOk)` и, если
   тот возвращал добивание, делал `applyForIntent(followUp, "reconcile")` — **и снова не вызывал
   `onRunFinished`**. Координатор оставался `running=true`; все последующие клики писались как
   «в ожидании» и **не выполнялись никогда**.
2. Сетевой receiver (`NetworkTtl.kt:509–560`) и `reapplyForNetwork` запускали скрипт **напрямую**,
   мимо координатора; отдельный `ttlInFlight` мог расходиться с его состоянием → сетевой ON
   пересекался с ручным OFF, и «последнее намерение» ничего не гарантировало.
3. `bootRestore` имел собственный путь записи `applied`.

**Изменение:**
- **Новый `tools/TtlRunner.kt`** — единственный владелец применения. Входы: клик
  (`request`), boot/сеть/возврат root (`onBackgroundTrigger`). Один `ReentrantLock`: параллельных
  shell-операций TTL нет по построению. Каждый проход завершается в хранилище
  (`markApplied`) и в цикле; догон последнего намерения ограничен `maxPasses=3`;
  исключение транспорта = **провал**, а не «применено»; при занятом локе клик не выполняется
  параллельно, а текущий цикл видит новое поколение и догоняет его.
- `tools/NetworkTtl.kt`: `setTtl65Active`, `bootRestore`, receiver, `reapplyForNetwork` переведены
  на раннер; **удалены** `ttlInFlight` и `reconcile`. `applied` привязан к **поколению намерения**
  (`ttl_65_intent_gen` / `ttl_65_applied_gen`) **и** к boot: результат прохода, во время которого
  намерение сменилось, публикуется как `pending reason=superseded`, а не как факт нового желания.
- §4.6: `isTtl65Active` больше не читает CPS напрямую — только через согласование копий
  (`Prefs2.readBoolean`); конфликт копий → «не ON», без перезаписи.
- Санация при `desired=OFF` идёт тем же путём (транспорт снимает **только свои** scoped-правила
  `oif wlan0`); Wi-Fi/CarPlay TTL не трогает; глобальных правил нет. **iptables ≠ TTL на проводе** —
  это по-прежнему не проверено на ГУ (⛔).

**Тесты (production-оркестратор, а не модель):** `Iter47Test` — OFF во время ON + добивание;
новый ON после добивания реально запускается; exception в первом и во втором проходе; быстрые
клики сходятся к последнему намерению без шторма; сетевое событие во время прохода не теряется;
при OFF сетевой триггер **не включает**; boot не меняет намерение; конфликт хранилища блокирует
запись; несохранённое намерение не даёт «applied»; неизвестное намерение не угадывается;
4 потока кликов — `maxParallel=1`; OFF во время сетевого ON; возврат root **без** broadcast;
«смерть процесса» + возобновление; вытеснение факта (superseded). ✅ **JVM**

### 1.2 §6 CPS/DPS: гонки, tombstone, честный результат записи

**Причина:** `Prefs2` считал `max(rev)+1` без всякого протокола, **игнорировал результат
`commit()`**, ловил исключения; два писателя могли получить одну ревизию. `Toggles45.pickString`
возвращал `winner ?: other` — при новом **удалении** строки старое значение из второй копии
«воскресало». Часть production-кода читала CPS напрямую (`ToolsBackend.state()`,
`AppPerformance.getPrefs`).

**Изменение:**
- `Toggles45.resolveBoolean/resolveString` → `Resolved.Value | Deleted | Conflict | Unknown`.
  Равные ревизии с разными значениями = **конфликт** (порядок не выдумывается). Tombstone
  (`<key>#del`) перекрывает старое значение из другой копии. Миграция без ревизий — прежняя
  семантика (настройки не теряются).
- `Prefs2`: `putBooleanEx/putStringEx/removeEx` → `Save(confirmed, stores, rev, conflict, reason)`;
  значение + ревизия + владелец + tombstone пишутся **одной транзакцией** в каждую копию, результат
  проверяется чтением. `getBoolean/getString/readBoolean` — через `resolve*`.
- Потребители переведены на общий путь: `ToolsBackend.state()` и запись тумблеров,
  `AppPerformance.isAutoOptimizeEnabled/isVideo60FpsEnabled`.
- **Чего не обещаю:** атомарности между CPS и DPS нет (два независимых `commit()`); «одна
  запись одной транзакцией в одну копию» ≠ межпроцессная атомарность SharedPreferences.
  Direct boot: чтение идёт по обеим копиям, tombstone виден и там.

**Тесты:** 6 тестов `resolve*` (последняя запись; конфликт равных; tombstone не воскрешает;
частичная запись → `Unknown`, а не «вторая копия права»; legacy без ревизий). ✅ **JVM**

### 1.3 §5 Звук: гонка «OFF во время bind» и чужой mount

**Причина:** поколение проверялось **до** `AdbClient.execute(bindScript)`; OFF/смена WAV во время
уже отправленного скрипта приводили к записи `applied` для **устаревшего** выбора. Все задачи
писали в **один** staging-файл `/data/local/tmp/carlock_custom.wav` — параллельная задача могла
подменить содержимое между копированием и bind. Скрипт снимал **любой** слой на цели
(`/vendor/etc/carlock/*.wav`), не проверяя, чей он. `applied` ставился по одному успешному mount.

**Изменение (`tools/LockSound.kt`):**
- staging уникален: `/data/local/tmp/carlock_custom_g<gen>_<crc32>.wav`; после использования
  удаляется (`cleanupStage`).
- после ответа скрипта намерение и поколение проверяются **заново**: если изменились — факт для
  этого поколения **не публикуется**, выполняется ограниченная **сходимость**
  (`convergeAfterBind`, флаг `convergePending` без лавины): OFF → снять только свои слои,
  другой файл → новый bind (новое поколение).
- реестр владения: `target|source|gen` (`OwnMount`). Снятие смотрит **фактический источник** слоя
  в `/proc/mounts` и снимает только `/data/local/tmp/carlock_custom*` (или записанный свой
  источник); чужой → `UNMOUNT_SKIP:…:foreign:`.
- `applied` — только если смонтированы **все** цели, найденные на устройстве
  (`expectedTargets`), иначе `pending reason=partial_mounts:N/M`.
- Временный отказ root (`ERR_ROOT_CHANNEL_UNAVAILABLE`, `Permission denied`, `avc: denied`)
  остаётся временным (iter46): backoff 5/10/20/40 с, ≤ `MAX_BIND_RETRIES`, повтор по «канал готов»,
  сброс при включении/смене файла/boot, отмена по поколению.
- **uninstall:** честно — если систему удаляют, код приложения не вызывается, и снять свои bind
  некому. Штатный звук вернётся после перезагрузки ГУ (bind-слои живут в namespace до ребута);
  проверить это на 1.0.63 я не мог. ⛔

**Тесты:** `offCancelsPendingWorkByGeneration`, `backoffIsBoundedAndGrows` (iter46) +
`parseOwnMount`/`isOurStageSource` (реестр владения, поколение, старый формат) — в `Iter47Test`. ✅ **JVM**
Физическая слышимость — только владелец. ⛔

### 1.4 §8 Логи: транзакционная ротация, spill, NUL внутри файла

**Причина:** `FileLogCore` удалял `.1` **до** переименования активного файла → отказ на следующем
шаге терял прежнюю часть. При занятом межпроцессном локе строка **отбрасывалась** (только
logcat-сообщение). Проверка хвоста не находила блок NUL, лежавший **внутри** датированного файла.

**Изменение:**
- **Ротация транзакционна:** строка сначала пишется в `<name>.new` (+`fsync`), затем активный
  файл заменяет `.1` (rename поверх — атомарно), затем `.new` становится активным. Отказ на любом
  шаге данные не теряет; при невозможности ротации — дозапись в активный файл с честным `reason`.
- **Spill вместо потери:** лок занят → строка в `<name>.<pid>.spill` (файл **своего** процесса,
  лок ему не нужен) + сообщение `LOG_SPILLED`; при следующей успешной записи spill вливается
  (`drainSpill`) и удаляется. В основной файл вне лока не пишем (источник «дыр»).
- `AppFileLogger`: `LOG_WRITE_FAILED` / `LOG_SPILLED` / `LOG_WRITE_UNLOCKED` — провал не
  подменяется успехом; порядок «проверить NUL до первой записи» сохранён (iter46).
- `LogFiles.scanNulBlocks` + `reportNulBlocks` (вызов из `prepare`): поиск блоков `0x00`
  **в любом месте** частей (до 4 МиБ на файл), факт `LOGFILES_NUL_DETECTED … where=файл@смещение:длина`.
  Файл **не переписывается и не обрезается**; происхождение блока по этим данным **не
  устанавливается** (это по-прежнему открытый вопрос — воспроизведения нет).
- `LogFiles.critical`: отказ межпроцессного лока — явный факт (`LOGFILES_LOCK_UNAVAILABLE …
  action=write_under_jvm_lock_only`), и **межпроцессно безопасной** эта запись не называется:
  координация в таком режиме только внутри процесса (честно указано и в коде, и здесь).

**Тесты:** 9 тестов iter46 + 4 новых: транзакционная ротация при занятом `.1` (данные целы),
успешная ротация с переносом обеих частей, spill при **реально удерживаемом** локе + слияние,
spill-файл на процесс, внутренний NUL найден с указанием смещения и файл не изменён, чистый файл
блоков не даёт. ✅ **JVM** (реальные файлы). Сквозной Android-тест `AppLog → файл` — ⛔ недоступен.

### 1.5 §9 Окна: поздний readback не должен снимать живую запись

**Причина:** поздний readback снимал запись владельцев, если набор **сейчас** пуст — но между
попыткой и readback окно могли снова открыть, и запись уже не пуста… либо её успели изменить.
Одного «пусто сейчас» недостаточно.

**Изменение:** снимаем только если набор **не изменился** с момента попытки
(`ownersAtAttempt == now && now.isEmpty()`), иначе `VENT_CLOSE_LATE_KEPT reason=owners_changed_since_attempt`.
Никаких повторных движений; `physical_failure=not_claimed` сохранено. ✅ **JVM-модель** правила.

### 1.6 §7 JIT: проверяемый выход из `chain_undefined`

**Что было:** единственным выходом из «неопределённости» был таймер 15 минут — это разблокировка
по времени, а не доказательство.

**Изменение:** добавлен **read-only** признак `JitNetState.zygoteStartMs()` (реализация —
`/proc/<zygote>/stat` field 22 + `/proc/uptime`, только чтение) и чистое правило
`JitOp.zygoteRestartEvidence(mark, zygoteStart, now)`: если zygote стартовал **после** отметки
операции (с допуском 60 с на сетку `starttime`), команда `ctl.restart zygote` была доставлена и
выполнена — «выполниться позже» она не может. Тогда новый **пользовательский** клик разрешается с
логом `JIT_UNDEFINED_RESOLVED evidence=zygote_restarted`, и прямо пишется, что это доказательство
**доставки команды**, а не того, что JIT-компиляция произошла. Нечитаемое время, отметка «из
будущего» (коррекция часов) и zygote, стартовавший раньше отметки, доказательством **не** считаются.
Автоматического повтора JIT нет: решает владелец кликом (`ctl.restart zygote` — ровно одно место,
только в цепочке клика). Таймер остаётся резервной границей.

**Не сделано в этой итерации (честно):** гонки записи/откат JIT-хранилищ (`JitRef.commitConditional`,
`assessStored`, `removeOwned`) переписаны в iter40–44 и **не ревизовались заново**; `umount`/namespace
(§7.3) — данных с ГУ нет, обратимость не заявляется; фактическая JIT-компиляция ничем из
доступного не доказывается. ⛔

## 5. §9 AVAS: что именно есть, а что нет

Заявленной ранее «read-only диагностики AVAS» как отдельного экрана **нет**. Есть ровно одна
read-only проверка: `AppPerformance.reportLegacyAvasSnapshot` — пишет строку
`AVAS_LEGACY checked=avas_mode_saved,avas_snapshot,avas_snapshot.tmp present=… files_found=N
action=none write=none value=not_read apply=none boot=…`. Реально получаемые поля: имена
проверяемых файлов, какие из них **существуют**, их число, тег загрузки. Режим/тип звука AVAS
**не читаются и не выставляются**, mute не включается, `audioserver` и системные звуковые файлы
не трогаются. Симптом 1.0.62 («вернулся, но в салоне не звучал») этим не объясняется. ⛔

### 7.5 Политика завершения JIT (как есть теперь)
1. Отметка операции `sending` → после ответа `replied`; нет ответа → `undefined` (неопределённость).
2. Пока неопределённость не снята — новый клик заблокирован (`chain_undefined`), маркер **не стирается**.
3. Выход из неопределённости: **(а)** доказательство — zygote стартовал после отметки
   (`JIT_UNDEFINED_RESOLVED evidence=zygote_restarted`); **(б)** резервная граница 15 минут
   (`JIT_OP_EXPIRED`) — это разблокировка по времени, не доказательство.
4. Автоматических повторов JIT и применения после boot нет; `ctl.restart zygote` — только клик.
5. Чего политика не даёт: подтверждения, что компиляция произошла; гарантий для `umount`/namespace.

### 7.7 Безопасный согласованный план проверки владельцем
Исходное состояние зафиксировать **до** действий: Wi-Fi включён/выключен, любой сайт открывается,
CarPlay работает, тумблеры TTL/звука — как сейчас.
1. Установить 1.0.63. Открыть «Инструменты» **холодным** стартом: включённые тумблеры видны сразу,
   без первого клика; выключить один — остальные не меняются.
2. TTL: включить → выключить раздачу телефона → включить обратно. Ожидаемо: тумблер остаётся ON,
   в логе `TTL_INTENT`, `TTL_PASS`, при отсутствии uplink — `applied=pending`, не «off».
   Быстро: включить и сразу выключить; через 10 с в логе должен быть проход с `want=false`.
3. Звук: сменить WAV → дождаться `VERIFY lockSound: SUCCESS` / `PARTIAL`; выключить звук —
   `LOCKSOUND_CONVERGE action=restore_stock`, штатный звук. Слышимость — ушами.
4. JIT: **один** клик при исходно включённом Wi-Fi. Снять: скриншот до/после, строки
   `JIT_START`, `JIT_CHAIN`, `JIT_UNDEFINED*`, `JIT_NET_RESTORE`, `TTL_*`. Повторный клик ради
   «починки Wi-Fi» **не делать** — он снова запускает `umount`/`zygote`.
5. Сеть после JIT: если Wi-Fi не поднялся — включить штатными настройками ГУ и снять read-only
   диагностику (`JIT_NET_RESTORE`, `wifi_enable=…`, `internet=not_checked`). Перезагрузка ГУ как
   лечение — не применять.
6. Логи: выгрузить датированный файл и `voiceapp3.log`; при желании — `grep -a`, оригиналы не менять.
